1项目概述

1.1 项目背景

本项目源于发起人参加湖南省高等教育自学考试(软件工程本科)备考过程中的实际痛点。考生以碎片时间备考,面临三个具体困难:一是纸质真题无法随时随地使用,通勤、排队、午休这些零散时间难以利用;二是做过一遍的错题没有系统记录,反复在同一个知识点上出错;三是缺乏外部提醒机制,容易连续多日中断学习。

已有的商业备考工具面向大众用户,功能繁杂且无法容纳考生自己整理的真题,数据也不在本地。因此本项目定位为一套个人专用的备考系统。

1.2 项目目标

  1. 碎片可用 —— 打开即做题,从启动到第一道题不超过两次点击。
  2. 真题驱动 —— 能把历年真题批量录入并结构化存储,按科目、章节、题型组织。
  3. 复习自动化 —— 用间隔重复算法自动安排错题的复习时间,考生只需完成当日任务。
  4. 提醒可靠 —— 每天定时推送带具体任务数量的系统通知,防止学习中断。

1.3 项目范围

包含:题库管理(录入、检索、编辑)、练习与判分、错题本与复习排期、学习数据统计、定时提醒推送、多端访问(手机 + 电脑)。

不包含:多用户与账号体系、社交功能(排行榜、分享)、在线支付、视频课程、题目自动判分(主观题由考生自评)、移动端原生应用。

1.4 术语约定

术语含义
科目一门课程,如「马克思主义基本原理概论」,用课程代码标识
章节科目下的知识单元
题型题目的形式,分客观题与主观题两类
客观题有唯一正确答案、可自动判分的题型(单选、多选、判断、英语各客观题型)
主观题需要参考要点自评的题型(简答、论述、材料分析、写作)
练习场次一次刷题过程,包含若干题目
复习队列进入间隔重复排期的题目集合,即错题本
到期按排期算法计算出「今天应该复习」

2需求分析

2.1 用户特征

项目描述
用户数量1 人,即考生本人
使用设备安卓手机为主(刷题),电脑为辅(录题、看统计)
使用场景通勤、排队、午休、睡前,单次 3—15 分钟
技术背景软件工程专业在读,能自行启动和维护本机服务
备考目标达到 60 分及格线

2.2 功能性需求

FR-1 科目与章节管理

系统应支持维护科目信息(课程代码、名称、简称、标识色、考试日期与场次)和章节结构,科目数量在 4—20 门之间,章节支持两级。

FR-2 题库录入

系统应支持三种录入方式:单题表单录入、批量 JSON 导入、粘贴试卷文本自动解析。批量导入必须支持部分成功——单条校验失败时跳过该条并报告原因,不影响其余题目入库。

FR-3 题库管理

系统应支持按科目、章节、题型、年份筛选题目,支持题干关键词全文检索,支持题目的增删改查。

FR-4 练习与判分

系统应支持五种练习模式:每日任务、随机练习、章节专项、整卷模拟、错题复习。客观题由系统自动判分;主观题展示参考答案要点,由考生勾选自行评估得分。

FR-5 错题与复习排期

系统应把答错的题目以及「答对但没把握」的题目加入复习队列,按间隔重复算法计算下次复习时间,并在每日任务中优先安排到期题目。

FR-6 学习统计

系统应提供累计练习量、平均正确率、连续打卡天数、各科目正确率、章节掌握度、近 30 天趋势等统计数据。

FR-7 定时提醒

系统应在考生设定的时间通过系统通知推送提醒,通知内容必须包含当日具体任务量(如「今日 12 题待复习,其中《马原》5 题」)。系统还应提供可选的晚间提醒,在当天未学习时发送,且每天最多一次。

FR-8 设置管理

系统应允许考生配置每日任务题量、提醒开关与提醒时间、界面主题。

2.3 非功能性需求

类别要求
性能页面首屏加载 ≤ 2 秒;提交答案响应 ≤ 500 毫秒;支持 5 万道题目的存储与检索
可用性手机上从打开到第一道题不超过 2 次点击;单次任务可在 5 分钟内完成
可靠性答题记录逐题即时保存,中途退出不丢进度;提交失败必须提示重试,不允许静默丢失
安全系统仅在本机或局域网内运行,不暴露公网;不收集任何个人信息
兼容性支持 Chrome 及基于 Chromium 的安卓浏览器;桌面端支持 Chrome 与 Edge
可维护性文档驱动开发;代码结构按业务域划分;关键算法有单元测试
成本零服务器成本,全部运行在考生自有设备上

2.4 约束条件

  1. 发布渠道限制:系统不通过应用商店分发,直接在本机运行,因此无需处理软件著作权登记与备案。
  2. 浏览器安全上下文限制:浏览器推送通知要求 HTTPS 或 localhost。手机通过局域网 HTTP 地址访问时无法注册通知,需通过内网穿透或证书解决。这是本项目最主要的技术风险。
  3. 主观题判分限制:中文主观题无法可靠地自动判分,采用考生自评方案。
  4. 开发资源限制:单人开发、业余时间进行,因此架构上刻意保持简单,不引入微服务、缓存中间件、消息队列等组件。

3技术选型

3.1 总体架构

系统采用前后端分离的单体架构。前端为单页应用(SPA),后端为 Java 单体服务,数据库为关系型数据库。前端以渐进式 Web 应用(PWA)形式安装到手机主屏幕,以获得接近原生应用的使用体验与通知能力。

┌──────────────────────────────────────────────┐
│  手机浏览器 / 电脑浏览器                       │
│  Vue 3 SPA（PWA，可安装到主屏幕）              │
│  ┌────────────────────────────────────────┐  │
│  │ Service Worker —— 接收推送、离线缓存    │  │
│  └────────────────────────────────────────┘  │
└───────────────────┬──────────────────────────┘
                    │ HTTP / JSON (REST)
┌───────────────────▼──────────────────────────┐
│  Spring Boot 单体服务（:8080）                │
│  控制器层 → 服务层 → 持久层                    │
│  定时任务：每分钟检查并触发提醒推送            │
│  生产环境同时托管前端静态资源                  │
└───────────────────┬──────────────────────────┘
                    │ JDBC
┌───────────────────▼──────────────────────────┐
│  MySQL 8（utf8mb4）                          │
└──────────────────────────────────────────────┘

3.2 前端技术选型

技术选型理由
框架Vue 3组合式 API 学习曲线平缓;单文件组件适合单人维护
构建工具Vite 5开发服务器启动快,热更新体验好
语言TypeScript 5前后端字段在编译期校验,避免接口不一致导致运行时报错
路由Vue Router 4官方方案
状态管理Pinia 2官方推荐,API 比 Vuex 简洁
UI 组件库Element Plus组件齐全、中文文档完善,降低界面开发成本
HTTP 客户端Axios生态成熟,拦截器机制便于统一处理错误
PWAvite-plugin-pwa支持安装到主屏幕与自定义 Service Worker
图表ECharts按需引入后体积可控,图表类型齐全

未选用的方案及原因:React(学习成本更高,对本项目无额外收益)、Tailwind CSS(与组件库样式体系冲突)、Nuxt(不需要服务端渲染)。

3.3 后端技术选型

技术选型理由
语言Java 17 (LTS)开发者主技术栈,可直接复用既有知识
框架Spring Boot 3.2企业主流,生态完整,本项目本身可作为工程实践素材
Web 层Spring Web MVC与 Boot 集成
持久层Spring Data JPA本项目查询以筛选与分页为主,可大幅减少模板代码
数据库迁移Flyway版本化建表脚本,可追溯、可回滚,优于 Hibernate 自动建表
参数校验Spring Validation声明式校验,减少手写判断
定时任务Spring @Scheduled内置能力,满足每分钟检查提醒的需求
推送Web Push (VAPID)标准协议,配合 Service Worker 实现系统级通知
接口文档springdoc-openapi自动生成 OpenAPI 描述,供前端生成 TypeScript 类型
构建MavenJava 生态默认选择

未选用的方案及原因:Node.js 或 Python 后端(与开发者主栈不一致,学习收益低)、MyBatis(本项目 SQL 复杂度低,无明显优势)、微服务架构(单机应用拆微服务属于过度设计)、Redis(数据量在万级以内,直接查询数据库足够)。

3.4 数据库选型

技术选型理由
数据库MySQL 8.0与 Spring Boot 组合最成熟,资料丰富,对硬件要求低
字符集utf8mb4 / utf8mb4_unicode_ci正确存储中文与生僻字
引擎InnoDB支持事务与外键,保证答题记录的一致性

未选用的方案及原因:SQLite(更轻量但报表 SQL 能力受限)、PostgreSQL(技术上更优但对本项目无决定性优势)。

特殊设计:题目选项与主观题参考答案要点采用 JSON 类型存储。原因是不同题型的选项结构差异较大,拆分为独立的选项表会使录入与查询都更复杂,而本项目不需要对选项做 SQL 层面的条件筛选。

3.5 关键技术方案:提醒推送

提醒是本项目的核心需求,也是技术选型中最需要论证的部分。方案如下:

1. Spring Boot 定时任务每分钟执行一次
2. 检查当前时间是否等于用户设定的提醒时间（允许 ±1 分钟误差）
3. 查询当日到期复习题数量，若为 0 则不推送
4. 通过 Web Push 协议（VAPID 密钥对）向该用户的浏览器订阅端点发送消息
5. 手机端 Service Worker 接收消息，调用系统通知接口弹出通知
6. 用户点击通知，跳转到复习页面
7. 写入推送日志，保证同类提醒每天只发一次
为什么不用微信小程序 小程序无法在用户未交互的情况下主动推送消息,而本项目的提醒是每日固定时间的主动推送,需求不匹配。这是本项目在早期技术选型中排除小程序方案的决定性原因。
已知风险 浏览器推送要求安全上下文(HTTPS 或 localhost)。手机通过局域网 HTTP 地址访问时无法使用通知功能。应对方案为内网穿透或自签名证书。

4.1 实体清单

科目一门课程课程代码、名称、简称、标识色、考试日期、考试场次

4.2 主要关系

科目与章节为一对多;章节与题目为一对多;科目与题目为一对多;试卷与题目为多对多(通过试卷题目表);练习场次与作答记录为一对多;题目与复习队列为一对一。

4.3 关键设计决策

复习队列独立成表。错题信息不放在题目表上,因为复习状态属于「学习者与题目的关系」,而非题目本身的属性。这样设计也让「将来若变为多用户」时无需改造题目表。

作答记录保存把握程度。除对错外,额外记录考生作答时是否自信。这使复习排期能区分「真会」与「蒙对」,显著提升复习效率。

唯一索引保证幂等。作答记录表在「练习场次 + 题目」上建立唯一索引,确保同一场次内同一道题只能作答一次,使重复提交安全。

全文索引使用 ngram 解析器。MySQL 默认全文解析器不支持中文分词,题干检索必须使用 ngram 解析器,否则中文关键词无法命中。

5.2 核心算法:间隔重复排期

排期采用简化的 SM-2 算法。每道进入复习队列的题目维护三个参数:复习阶段(整数,初始为 0)、间隔天数(初始为 1)、难度系数(初始为 2.5)。

作答结果排期调整
答错阶段归零,间隔重置为 1 天,难度系数减 0.2(下限 1.30)
答对但没把握阶段不变,间隔重置为 1 天
答对且确定阶段加一,间隔 = 上一间隔 × 难度系数;连续答对 4 次后标记为已掌握,移出队列

间隔天数上限设为 60 天,避免出现长期不再复习的情况。

5.3 核心流程:每日学习

  1. 考生在设定时间收到通知:「今日 12 题待复习,其中《马原》5 题,《英语》7 题」。
  2. 点击通知进入应用,首页显示今日主任务按钮。
  3. 点击开始,系统优先抽取到期复习题,不足部分用新题补足至设定的每日题量。
  4. 逐题作答,每答一题立即保存。
  5. 客观题即时判定并展示解析;主观题展示参考答案要点,由考生勾选自评。
  6. 练习结束展示本轮成绩,系统更新复习队列与当日学习日志。
  7. 若当天未学习,晚间提醒再次推送一次(每天最多一次)。

6界面设计

界面设计遵循三条原则:一屏一件事(每页只回答一个问题)、三秒可开始(打开到第一道题不超过两次点击)、数字即反馈(用数据而非徽章激励)。

主要页面包括:今日首页、刷题页、本轮小结、题库管理、题目编辑、批量导入、错题本、数据看板、科目管理、设置与提醒。

完整的配色方案、字体规范、组件规格、响应式断点与交互细节,见配套文档《UI 设计规范》(docs/design/ui-design-spec.md)。

8风险与对策

风险影响对策
浏览器推送要求 HTTPS,局域网 HTTP 环境无法注册通知提醒刚需无法实现采用内网穿透或自签名证书;开发期在桌面端 localhost 验证推送链路
国产手机系统的浏览器/系统会限制后台通知通知收不到引导用户将应用添加到主屏幕、在系统设置中允许通知;提供通知状态自检页面
主观题自评尺度不一致统计数据失真正确率统计仅计入客观题,主观题单独统计自评得分
真题录入工作量大项目推进受阻优先实现批量导入;题目格式规范化后可由工具批量生成
单人开发时间有限项目中断分阶段交付,每阶段独立可用;优先级上题库先于练习
间隔重复算法参数不当复习节奏不合理算法逻辑编写单元测试;参数在文档中明确并可配置
